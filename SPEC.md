# ТЗ: платформа «Assistant» — личный помощник, команда, рабочие утилиты

Этот файл — главный источник правды для разработки. Читай его в начале каждой сессии.
Текущий статус этапов веди в файле `STATUS.md` (создай его на этапе 0 и обновляй после каждого этапа).

## 0. Контекст

Заказчик — руководитель в trade marketing (табачная компания, рынок Узбекистана). Один человек разрабатывает «для себя и команды». Нетехнический пользователь: пиши отчёты и вопросы простым русским языком, без лишнего жаргона.

Платформа решает три задачи:
1. **Личный помощник** — задачи, календарь, напоминания, ввод голосом через Telegram.
2. **Управление командой** — задачи сотрудникам, согласования, встречи и минутки, карточки сотрудников.
3. **Рабочие утилиты** — модули под конкретные задачи. Первый: **планограммы** (раскладка продукции на торговом оборудовании).

## 3. Архитектура: ядро + модули

Модульный монолит. Структура:

```
/app                 Next.js маршруты (UI + API routes)
/modules
  /core              пользователи, роли, auth, уведомления, настройки
  /tasks             задачи, планы, календарь, связи
  /meetings          встречи, минутки
  /team              карточки сотрудников
  /planograms        планограммы
  /bot               Telegram-бот (команды, голос, карточки подтверждения)
  /ai                обёртка над Claude: промпты, парсинг JSON, лимиты
  /stt               распознавание речи
/lib                 общие утилиты (дата/время, i18n, логирование)
/prisma              schema.prisma, миграции, seed
/docs                DECISIONS.md, SETUP-SERVER.md, USER-GUIDE.md
```

Каждый модуль:
- имеет свою часть Prisma-схемы (все модели в одном `schema.prisma`, сгруппированы комментариями по модулям);
- свой сервисный слой (чистые функции, тестируемые без HTTP);
- свои API-роуты и UI;
- регистрируется в реестре модулей ядра: название, иконка, кому доступен (роли).

## 4. Общие требования

### 4.1 Пользователи и роли
- Вход через Telegram (Telegram Login Widget на вебе; в боте пользователь идентифицируется по `telegram_id`). Паролей нет.
- Первый вошедший пользователь становится `OWNER`. Остальные попадают в систему только по приглашению (одноразовая ссылка/код от OWNER или MANAGER).
- Роли: `OWNER` (всё), `MANAGER` (управляет своей командой и утверждает задачи), `MEMBER` (свои задачи и то, что ему назначено). Доступ к модулям настраивается по ролям.
- Личные данные (личные задачи, личные заметки) видит только их автор. OWNER не видит личные задачи сотрудников.

### 4.2 Уведомления
Единый сервис `notify(userId, event)`: пишет в таблицу уведомлений (для UI) и отправляет в Telegram, если у пользователя привязан бот. У пользователя — настройки: какие уведомления получать, «тихие часы».

### 4.3 ИИ
- Все вызовы Claude — через `/modules/ai`. Каждый промпт — отдельная функция с типизированным результатом (zod-схема). Ответ модели всегда запрашивается в JSON, парсится и валидируется; при ошибке — одна повторная попытка, потом понятная ошибка пользователю.
- Логируй расход токенов по каждому вызову в таблицу `ai_usage` (пользователь, функция, токены, дата) и показывай OWNER сводку за месяц.
- Дневной лимит вызовов на пользователя (env `AI_DAILY_LIMIT`, по умолчанию 200).

### 4.4 Безопасность и данные
- Валидация всех входных данных (zod).
- Rate limit на API и на бота.
- Журнал действий (`activity_log`): кто, что, когда изменил — для задач, планограмм, карточек.
- Скрипт ежедневного бэкапа PostgreSQL (`pg_dump` в папку + ротация 14 дней) — на этапе деплоя.

## 5. Этапы разработки

### Этап 0. Каркас проекта
- Инициализировать Next.js + TypeScript + Tailwind + shadcn/ui.
- Prisma + PostgreSQL, docker-compose для dev.
- Vitest, ESLint, Prettier, typecheck. Скрипты: `dev`, `build`, `test`, `lint`, `typecheck`, `db:migrate`, `db:seed`.
- GitHub Actions: lint + typecheck + test на push.
- `README.md` (как запустить локально, на русском), `STATUS.md`, `docs/DECISIONS.md`, `.env.example`.
- PWA: manifest, иконки-заглушки, service worker (базовый offline для оболочки).
- **Готово, когда:** `npm run dev` поднимает пустое приложение со страницей «Assistant», CI зелёный.

### Этап 1. Ядро: вход, роли, бот-скелет, уведомления
- Модели: `User`, `Invite`, `Notification`, `UserSettings`, `ActivityLog`.
- Вход через Telegram Login Widget, сессии (cookie, httpOnly).
- Первый пользователь = OWNER; приглашения; страница «Команда» (список пользователей, роли, приглашения).
- Бот (grammY): `/start` (привязка аккаунта по инвайт-коду или если пользователь уже есть), `/help`. Webhook + long-polling режимы.
- Сервис уведомлений + страница уведомлений + настройки.
- Базовый layout: нижняя навигация на мобильном, боковая на десктопе, реестр модулей.
- **Готово, когда:** можно войти через Telegram, пригласить второго пользователя, оба получают тестовое уведомление в Telegram и в UI. Тесты на роли и приглашения.

### Этап 2. Модуль «Задачи»
- Модели: `Task`, `TaskDependency`, `Plan` (уровни: YEAR / MONTH / WEEK), `Comment`, `TaskAttachment` (ссылки/файлы, файлы хранятся на диске сервера, путь в БД).
- Поля задачи: заголовок, описание, исполнитель, постановщик, срок, приоритет, статус, проект/тег, родительский план, личная/командная, оценка времени.
- Статусы и переходы: `DRAFT → PENDING_APPROVAL → APPROVED → IN_PROGRESS → IN_REVIEW → DONE`, плюс `CANCELLED`. Личные задачи минуют согласование (`DRAFT → IN_PROGRESS`). Кто может переводить в какой статус — по ролям (MEMBER не утверждает).
- При `APPROVED` задача появляется у исполнителя и в календаре, уходит уведомление.
- Связи: «блокирует / зависит от». Нельзя закрыть задачу, пока не закрыты блокирующие. Подсветка цепочек.
- Планы: год → месяц → неделя; задача привязана к плану; у плана виден прогресс (% задач DONE).
- Представления: **Список** (фильтры: мои, команда, статус, срок, проект), **Канбан** по статусам (drag-and-drop), **Календарь** (месяц/неделя/день), **Таймлайн** (простой Gantt: задачи по датам, связи стрелками).
- Комментарии, история изменений в карточке задачи.
- Экран «Сегодня»: задачи на сегодня, просроченные, ждущие моего утверждения.
- **Готово, когда:** полный цикл — создать задачу сотруднику, он видит её только после утверждения, выполняет, вы принимаете. Тесты на переходы статусов и блокировки по зависимостям.

### Этап 3. Бот: задачи текстом и голосом
- Абстракция `SpeechToText` (см. стек). Для dev и тестов — mock-реализация.
- Текстовое или голосовое сообщение боту → STT (если голос) → `ai.extractTasks(text, context)` → список задач в JSON: `title, assigneeName?, dueDate?, priority?, project?`. Контекст для Claude: список сотрудников (имена), проекты, сегодняшняя дата и таймзона, язык пользователя. Модель должна понимать русский, узбекский и их смесь, относительные даты («в пятницу», «через неделю», «до конца месяца»).
- Сопоставление `assigneeName` с пользователями (нечёткое совпадение; если неоднозначно — спросить кнопками).
- Карточка подтверждения в боте с inline-кнопками: ✅ Сохранить / ✏️ Изменить (срок, исполнитель, название — через кнопки и короткий диалог) / ❌ Отмена. Несколько задач из одного сообщения — одна карточка со списком.
- Команды: `/today`, `/week`, `/overdue`, `/pending` (ждут моего утверждения). Естественные запросы: «что у меня сегодня», «перенеси X на четверг», «закрой задачу X» → `ai.interpretCommand`.
- Утверждение задач прямо из бота (кнопки ✅/❌ в уведомлении).
- **Готово, когда:** mock-STT и реальные промпты проходят тесты на 15+ примерах фраз (русский, узбекский, смесь, относительные даты, несколько задач). Ручная проверка с реальным Telegram — на этапе деплоя; до этого — тесты и dev-режим long polling, если доступен.

### Этап 4. Напоминания и дайджесты
- Планировщик на pg-boss. Задания: утренний дайджест (время настраивается, по умолчанию 08:30 по таймзоне пользователя), напоминание за день до срока, уведомление о просрочке (исполнителю и постановщику), пятничный итог по команде (для MANAGER/OWNER), напоминание за 15 минут до встречи (после этапа 5).
- Дайджест формирует Claude коротким текстом из структурированных данных: что сегодня, что горит, что ждёт утверждения. Fallback без ИИ — простой шаблон.
- Настройки уведомлений у пользователя, «тихие часы», отписка от отдельных типов.
- **Готово, когда:** в тестах планировщик корректно формирует задания для разных таймзон и не шлёт дубли.

### Этап 5. Встречи и минутки
- Модели: `Meeting` (название, дата/время, участники, повестка, ссылка), `MeetingNotes`.
- Календарь встреч (общий с календарём задач, разным цветом).
- Минутки: текст пишет пользователь (или присылает голосовым в бот → STT). `ai.extractActionItems(notes)` → список задач → карточка подтверждения (как в этапе 3) → задачи создаются со ссылкой на встречу.
- Повторяющиеся встречи (еженедельно).
- **Готово, когда:** из текста минуток корректно создаются задачи с исполнителями и сроками; тесты на извлечение.

### Этап 6. Карточки сотрудников
- Расширение `User`: должность, зона ответственности (scope), контакты, дата начала, руководитель.
- Автоматическая статистика по задачам: активные, просроченные, % вовремя за 30/90 дней, средняя длительность, загрузка по неделям (мини-график).
- Приватные заметки руководителя: сильные стороны, зоны роста, заметки с 1:1, цели развития. **Видны только OWNER и прямому руководителю.** Сотрудник не видит. В UI называть «Сильные стороны» и «Зоны роста», не «плохие качества».
- Экран команды: сетка карточек с загрузкой, фильтры.
- **Готово, когда:** статистика считается правильно (тесты на расчёт), приватность заметок проверена тестами на доступ.

### Этап 7. Модуль «Планограммы»
Подробное описание предметной области, типов оборудования и правил — в `docs/PLANOGRAM-INPUT.md` (обязательно прочитай перед началом этапа). Примеры реальных планограмм заказчик загружает в `docs/planogram-examples/`.

**Ключевая идея модуля:** планограмма — это не картинка, а **данные** (оборудование + слоты + SKU + цены + POSM). Картинка (PPTX/PDF/PNG) генерируется из данных. Тогда повышение цен, замена SKU или добавление новинки делается один раз и применяется ко всем планограммам сразу.

- **Модели:**
  - `Equipment` — тип оборудования: код (напр. `DISPLAY_L`, `MODULE_9x2`, `LEGO_21`, `POG_MINI`), название, канал (`POSI`, `MW`, `DG`, …), геометрия как **список полок**, у каждой полки — список слотов (слот = одна ячейка под один facing). Для нестандартных форм (LEGO) полки могут иметь разное количество слотов и смещение. Схема хранится в JSON, чтобы любую форму можно было описать без изменения кода.
  - `Sku` — бренд (ESSE, BOHEM, PINE, …), название варианта, код, формат, картинка пачки (загружается), бейджи по умолчанию (напр. `1mg`), флаг «новинка» и дата, флаг «обязательный SKU».
  - `PriceList` / `SkuPrice` — цена каждого SKU с датой начала действия. **Ценник на планограмме берётся из прайс-листа**, а не хранится в слоте. Повышение цен = новый прайс-лист с датой, все планограммы обновляются автоматически; старые версии сохраняют старые цены.
  - `Posm` — POSM-элементы: хедер/баннер (над полками), промо-баннер (занимает целую полку или часть), стикер/вобблер в слоте (напр. `YANGI`, `ENDI 1MG`, `KAPSULALI YASHIL`, `BU YERDA`), ценовая выноска. У каждого — картинка, тип и сколько слотов занимает.
  - `Planogram` — оборудование, канал, название, период действия (с… по…), статус `DRAFT / PENDING_APPROVAL / APPROVED / ARCHIVED`, версия, ссылка на предыдущую версию.
  - `PlanogramSlot` — полка, позиция, что в слоте: `SKU` (+ бейджи: `YANGI`, `1mg`, `2mg`, …) или `POSM` или пусто.
  - `PlanogramRule` — правила валидации (см. ниже).
- **Библиотеки:** оборудование (визуальный конструктор геометрии: добавить полку, задать число слотов), SKU с картинками и ценами, POSM с картинками. Импорт SKU и цен из Excel/CSV.
- **Редактор:**
  - сетка полок и слотов строго по геометрии оборудования, картинки пачек в одном масштабе, ценник автоматически под каждым facing, бейджи поверх пачки;
  - drag-and-drop SKU и POSM из боковой панели; клик по слоту — заменить/очистить/добавить бейдж; выделить несколько слотов и залить одним SKU;
  - копирование полки, перемещение полки вверх/вниз, undo/redo;
  - панель «Изменения относительно предыдущей версии»: добавлено, удалено, перемещено (это заменяет ручные пометки `delete`, `Вниз`, выноски с ценами в PowerPoint);
  - работает на десктопе и планшете; на телефоне — просмотр и согласование.
- **Правила и валидация** (настраиваются, нарушения показываются в редакторе, утверждение блокируется при критичных):
  - обязательные SKU должны присутствовать (напр. «9 обязательных SKU из 18 — в переднем ряду»);
  - минимум/максимум facing на SKU;
  - бренд-блоки: SKU одного бренда рядом; порядок брендов (напр. ESSE → BOHEM → PINE);
  - новинки — с бейджем `YANGI` и на приоритетных полках;
  - каждый слот либо заполнен, либо осознанно помечен пустым.
- **Автозаполнение:** по выбранному оборудованию и набору правил система предлагает раскладку (детерминированный алгоритм: обязательные SKU → бренд-блоки → facing по приоритету). `ai.suggestLayout` — дополнительно, по текстовому описанию («сделай как на Display L, но для 6×3»), результат проходит ту же валидацию.
- **Массовые операции:**
  - **повышение цен:** загрузить новый прайс-лист с датой → предпросмотр всех затронутых планограмм → утвердить → у всех активных планограмм новая версия с новыми ценниками и автоматическим листом изменений;
  - замена SKU на другой во всех планограммах; добавление новинки во все планограммы выбранного типа на указанную позицию;
  - создание планограммы для другого канала/размера из существующей (адаптация с проверкой правил).
- **Шаблоны и версии:** сохранить как шаблон, создать из шаблона, история версий, сравнение двух версий бок о бок (before/after) с подсветкой изменений.
- **Согласование:** как у задач. Утверждённая планограмма доступна по ссылке без входа (по токену) для мерчендайзеров; печатная версия с крупными ценниками.
- **Экспорт:** PPTX (один слайд на планограмму: заголовок «Display L POSI», подзаголовок проекта, дата, версия, картинка планограммы; отдельный слайд «что изменилось» для before/after), PDF, PNG. Пакетный экспорт: все планограммы проекта в один файл. Фирменный шаблон слайда — заказчик пришлёт, до этого — нейтральный.
- Отправка утверждённой планограммы выбранным пользователям в Telegram (картинка + ссылка).
- **Готово, когда:** в seed описаны минимум 4 типа оборудования из `PLANOGRAM-INPUT.md` (Display L, Module 9×2, LEGO 21, POG MINI), 18 тестовых SKU с ценами; можно собрать планограмму, увидеть нарушение правила обязательных SKU, утвердить, выгрузить PPTX/PDF; загрузить новый прайс-лист и получить новые версии всех планограмм; тесты на геометрию, валидацию правил, расчёт изменений между версиями и применение прайс-листа.

### Этап 8. Деплой на VPS и эксплуатация
- `Dockerfile` (multi-stage), `docker-compose.prod.yml`: app, postgres, whisper (faster-whisper server, модель `small`, можно отключить), caddy (HTTPS, домен или поддомен из env).
- `docs/SETUP-SERVER.md`: пошаговая инструкция на русском для нетехнического пользователя: Ubuntu 24.04, создание пользователя, firewall (ufw: 22, 80, 443), установка Docker, клонирование репозитория, заполнение `.env`, первый запуск, миграции, настройка webhook бота, проверка.
- GitHub Actions deploy: при push в `main` — SSH на сервер, `git pull`, `docker compose up -d --build`, миграции. Секреты: `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`.
- Бэкапы: cron-скрипт `pg_dump` ежедневно, хранить 14 дней; инструкция восстановления.
- Мониторинг минимальный: healthcheck endpoint `/api/health`, уведомление OWNER в Telegram, если бот или планировщик упали (watchdog).
- `docs/USER-GUIDE.md`: короткое руководство для сотрудников (как войти, как работать с задачами в боте и в приложении).
- **Готово, когда:** на чистом сервере по инструкции всё поднимается с нуля за ~30 минут; реальный Telegram-бот отвечает; голосовое сообщение превращается в задачу.
